## Executive summary

WireMesh is **not one release away from v1.0; it is roughly one more phase away.** The
distance is not in the data plane — that part is genuinely good, and better than the docs
admit. WireGuard via boringtun, eBPF/nftables enforcement parity, NAT traversal, the relay
path, and (as of today, v0.9.1) in-step key rotation are all built and proven by netns
done-bars. The distance is in everything that turns working code into a product a stranger
can run: **five of the PRD's own P0 cross-cutting requirements are materially unmet
(X-1b, X-2, X-5, X-6, X-7), the spec's P0 OpenBao reference provider was deferred without
amending the spec, no CI job runs a single test, and the bare-metal install path cannot be
completed from the docs at all** — no user-facing document anywhere explains how to create a
segment, mint an enrollment token, distribute the CA, or write a policy. The strings
`fabricctl token`, `fabricctl segment create` and `fabricctl policy` appear in no doc a user
would read.

Two findings make a v1.0 tagged today **unsafe**, not merely incomplete, and they compound.
First, a packaged systemd controller ships with automatic key rotation **armed at the 30-day
default** — `deploy/packages/env/controller.env` leaves `WIREMESH_ROTATION_INTERVAL`
commented out and `wiremesh-controller/src/lib.rs:219` defaults to 30 days — while
`docs/install.md:73-83` presents that timer as a normal, safe feature. Only the Kubernetes
operator path is safe, and only because `workloads.rs:485` hardcodes `unwrap_or("off")`.
Second, the rotation wedge (backlog item 9) is **confirmed still open**: the first rotation
that fails for any reason parks that gateway off-`Idle` permanently and silently, ignoring
every later directive until the process restarts. So the shipped default arms a timer at a
trap the project already knows about. A package installer who does nothing gets a fabric that
begins silently wedging its gateways 30 days after install.

Third, quieter and larger: **the G-2 throughput gate has never been retired.** The PRD makes
it a carried Phase-0 go/no-go — *"if the cap reproduces on cloud, Bet 1 reopens before any
Cycle 4 gateway work"* — and Cycles 4a/4b/4c were built anyway. The only numbers that exist
are ~7.5–7.8 Mbit/s with 98% receive-side loss in the dev container, believed environmental
but never checked on real hardware (`docs/research/phase0-results.md:24`,
`crates/wiremesh-gateway/bench.md`). Nobody currently knows whether this fabric moves 1 Gbps
or 8 Mbit/s. That is a one-day experiment gating a v1.0 claim whose failure mode is
"replace the data plane".

One more, because it changes what "1.0" means: **X-6 version negotiation does not exist at any
layer**, and its failure mode was recently made silent. A gateway first-booting against a
too-new controller now attaches its default-deny enforcer, drops all fabric traffic, and
reports healthy to systemd and Kubernetes — the process crash that used to be the only signal
was removed in PR #43 without the negotiation that was meant to replace it. The fields to fix
it are designed, verified free at HEAD, and additive; **v1.0 is the last moment they are
cheap.**

The honest positive: this project's *self-knowledge* is exceptional. `docs/BACKLOG.md` is one
of the better engineering backlogs I have read, and most of what follows was already known
somewhere. But "known in `BACKLOG.md`" is not "said to the operator", and the release-blocker
test — *would a competent operator deploying from the docs alone hit something the project
knows about and did not say?* — fails on at least six counts. The self-knowledge is also now
drifting in **both** directions: three backlog items are stale *pessimistic* (item 3 fixed,
item 7's "delete it" advice would break a done bar, item 19's entire correctness justification
shipped in v0.6.0), one help-text block is stale *dangerous*, and `CLAUDE.md`'s PRD fold-in
note has the direction backwards. Realistic effort to an honest, deployable v1.0: **6–10
focused weeks**, of which maybe two are code and the rest is documentation, CI, packaging, and
the licence/security hygiene an Apache-2.0 release is expected to have on day one.

### B1. Packaged controller arms a known-broken rotation timer, and the docs recommend it
**Size: 1–2 days (doc + packaging), or 1–2 weeks if you fix item 9 first and ship it armed.**
`deploy/packages/env/controller.env` leaves `WIREMESH_ROTATION_INTERVAL` commented out;
`wiremesh-controller/src/lib.rs:219` (`Config::default_rotation_interval`) is 30 days;
`rotation_interval_from_env` (`lib.rs:441`) maps *absent* → 30d. `docs/install.md:73-83` and
the env template both describe the 30-day timer as the normal default and `off` as merely an
option. Meanwhile `BACKLOG.md:419` says `off` "must stay set" and `BACKLOG.md:150` records
that the v0.7.0 `off` escape hatch "defused a fabric-wide outage dated 2026-08-31".
The Helm/operator path is safe; the systemd/package path — the one `install.md` walks — is
not. **Minimum honest fix:** flip the packaged default to `off`, and rewrite the install.md
section to state why. **Dependency:** none, but see B2 — if item 9 lands first, this can
instead ship armed and honest.

### B2. Rotation wedge (backlog item 9) — one failed rotation silently kills a gateway forever
**Size: 3–5 days (~40–80 LOC + tests). CONFIRMED OPEN.**
`rotation.rs:Rotation::on_directive` (L65) honours a directive only from `RotationPhase::Idle`
(`_ => None`). `main.rs:handle_rotate` (L4188) commits the phase transition on its **first
statement** (L4196) and then does eight fallible things — desired-state lookup, key mint,
persist, `plan_tunnel`, `bring_up`, enforcer attach, `uapi::apply`, `submit_epoch_key`. Its
sole caller (`main.rs:1219`) only `eprintln!`s the error. Three confirmed routes park the
phase permanently:
1. `handle_rotate` errors before `role_a` is set → phase `Overlapping` with nothing driving it.
2. Stuck in `Overlapping` — `run_rotation_ticks` (L5046) advances only `if any_live`; no timeout.
3. Stuck in `CutOver` (L5235) — the code comments this itself: *"ROTATION WEDGED … THIS
   GATEWAY WILL SILENTLY IGNORE EVERY FURTHER RotateDirective UNTIL THE PROCESS RESTARTS."*

There is **no phase reset and no deadline anywhere**: the only assignment back to `Idle` is
`on_epoch_retired` (`rotation.rs:94`), reachable only from `CutOver`. Zero tests cover
`handle_rotate` (it lives in the binary). Fix shape: an `on_rotation_failed()` abort
transition plus a `phase_since: Instant` deadline in `run_rotation_ticks`, with
`handle_rotate` wrapped so every `Err` resets. **Gates:** re-enabling automatic rotation at
all, and therefore B1's "ship it armed" option, and PRD **C-5**.

### B3. G-2 throughput gate never retired — the data-plane go/no-go is still open
**Size: 1 day to measure; unbounded if it fails.**
PRD G-2 requires ≥1 Gbps single-flow and ≥1 Gbps aggregate over 8 tunnels on a 4-vCPU cloud
VM, and carries an explicit Phase-0 reopening condition. `docs/research/phase0-results.md:24`
: *"The G-2 gate itself … **remains unmeasured**"*, with a measured ~7.5–7.8 Mbit/s
receive-side cap and **98% loss** on `iperf3 -u -b 0` in-container, and `:106-109` naming the
loss check as the first thing to run on cloud. `crates/wiremesh-gateway/bench.md` says the
same and the smoke test *deliberately asserts no floor*. You cannot honestly ship a 1.0
network fabric without this number. **Dependency:** a cloud VM. **Risk:** if the cap
reproduces, Bet 1 reopens and boringtun is on the table — that is a phase, not a task.

### B4. No CI runs any test; the default `cargo test` is a false green
**Size: 1–2 weeks.**
Three workflows exist: `codeql.yml` (`workflow_dispatch` only — deliberately neutered in
favour of default setup), `container-images.yml` (builds images; on PRs builds without
pushing), `release.yml` (tags). **There is no `cargo test`, no `clippy`, no `fmt --check`, no
`cargo deny`/`audit`, no MSRV pin (`rust-version` is absent from all 11 crates and there is no
`rust-toolchain.toml`) anywhere in CI.** A PR that deletes assertions merges green; the only
gate is that the Dockerfile compiles, and only on path-filtered PRs.

Worse, the local story has the same hole. **14 of 45 gateway test files are behind
`#[cfg(feature = "netns-tests")]`**, including every file that proves the data plane works —
`nat_matrix`, `relay_matrix`, `convergence_matrix`, `key_rotation`, `mesh_milestone`,
`enforce_netns`, `routes_netns`, `throughput_bench`. `key_rotation.rs:1978` states it: *"Without
it this whole file compiles to zero tests and `cargo test` prints a green summary that proves
nothing."* This directly contradicts PRD **X-5** ("CI running the NAT-matrix and multi-segment
integration tests publicly"), **X-1** (CI platform smoke), **X-6** (skew matrix in CI) and the
spec §9 testing strategy in full. For an open-source project, no external contributor can
have their PR validated. **Dependency:** the netns/eBPF suite needs a privileged Linux
runner — solvable with a self-hosted or `ubuntu-latest` + privileged container job, but it is
real work.

### B5. OSS release hygiene absent — and the licence gap is a legal one
**Size: 3–5 days.**
`.github/` contains only `workflows/`. Missing entirely: **`SECURITY.md`** (no disclosure
contact, on a security product), **`CONTRIBUTING.md`** (README:130 points contributors at
`CLAUDE.md`, which is an AI-agent operating manual), **`CODE_OF_CONDUCT.md`**, issue/PR
templates, **`CHANGELOG.md`**, `ADOPTERS.md`, and a published **threat model** (PRD §10 says
"must be published with v1"; it currently exists only inside an internal design spec).
Directly fails PRD **X-5**, which the PRD itself marks "day one".

The sharp one is **`NOTICE` and third-party licence attribution: absent, with no tooling** —
no `deny.toml`, no `about.toml`, no `cargo-about`. You are shipping statically-linked
binaries containing boringtun, rustls, quinn, aya and a large transitive tree with no
attribution file. Under Apache-2.0 §4(d) that is an obligation, not a nicety.

### B6. Release integrity: X-7 unmet — nothing is signed
**Size: 2–4 days.**
`release.yml` produces `SHA256SUMS` (`release.yml:294`) and nothing else. Verified absent
across `.github/`, `deploy/`, `scripts/`: cosign, sigstore, minisign, GPG, SLSA provenance,
`actions/attest-build-provenance`, SBOM (syft/CycloneDX/SPDX). **The SHA256SUMS file is itself
unsigned**, so it is a corruption check with no authenticity. Apple signing is a *stub* that
prints "tracked follow-up" even when the secrets are present, so the `.pkg` ships
Gatekeeper-blocked and the MSI SmartScreen-warned. PRD **X-7** additionally requires a
one-line install script that verifies checksums before executing — **no install script exists
anywhere** (`scripts/` contains only `set-version.sh`), which also fails **X-1b**, where
`curl | sh` is P0.

### B7. Bare-metal deployment is not documented end-to-end
**Size: 1–2 weeks.**
`docs/install.md` walks you to a `wiremesh-gateway enroll` command at line 275 and stops. It
never tells you how to obtain the three things that command requires: an enrollment token, the
CA bundle on the gateway host, or the segment to enroll into. `fabricctl token mint`
(`fabricctl/src/main.rs:428`), `fabricctl segment create` (`:342`), `fabricctl policy` (`:477`)
and `fabricctl relay register` (`:400`) **appear in no user-facing document**. There is no
policy-DSL reference doc — the DSL is described only in an internal design spec — so even a
successfully enrolled pair passes zero traffic under default-deny and the operator has no way
to learn why. Fails PRD **X-4** ("two segments in 30 minutes") and Goal 1 outright. The
Kubernetes path (`docs/operator.md` §"Bring up a fabric") is the only walkable route, and it
pins `--set image.tag=v0.1.0` (nine releases stale) and ships only one gateway example.

### B8. Version stamping is broken — shipped binaries and the operator lie about their version
**Size: 2 hours.**
All **11 crates are hardcoded `version = "0.1.0"`** in git; the real version exists only
transiently in CI. `scripts/set-version.sh:22` stamps exactly four crates —
`fabricctl`, `wiremesh-controller`, `wiremesh-gateway`, `wiremesh-relay` — so
**`wiremesh-operator` is never stamped at all** despite being built and pushed as a container
image, and will self-report `0.1.0` forever. `deploy/helm/wiremesh-operator/Chart.yaml` is
likewise `0.1.0`/appVersion `0.1.0`. Anyone building from a git checkout gets binaries claiming
0.1.0. This is a blocker only because X-6 and every support conversation start with "what
version are you running".

### B9. README describes a project that no longer exists
**Size: 1 day.**
`README.md:9` — *"Status: pre-1.0 … **not yet a shippable end-to-end fabric**"*; `:68-73`
mark Cycle 3 "⏳ Next" and Cycle 4 "⏳ Pending" (both shipped); `:79-97` lists 5 crates against
14 on disk. **The README links to neither `docs/install.md` nor `docs/operator.md` and has no
"Getting started" section.** It also advertises the client peer (`README.md:5,19`) — see D4,
which has no code. A v1.0 whose front door says it is not shippable is not a v1.0.

### B10. X-6 version negotiation does not exist, and the failure mode is now a silent blackhole
**Size: ~1 day for the proto fields (the part that must land before the tag); 1.5–2.5 weeks
for all of X-6. CONFIRMED ABSENT at every layer.**
Verified directly: `proto/wiremesh/v1/{sync,enrollment,admin}.proto` contain no component
version, no minimum-supported-version, no capability set, no IR-schema advertisement.
`WatchRequest` has exactly one field. `env!("CARGO_PKG_VERSION")` appears only in `--version`
output and never reaches the wire. `check_session_generation` (`sync.rs:580`) is a per-boot
liveness nonce for rejecting a report from a gateway's *previous process* — a different
mechanism, and confusing the two would be a category error.

What makes this a blocker rather than a should-fix is the current failure mode.
`PolicyIR::from_json` rejects `schema != 1` (`wiremesh-policy/src/ir.rs:85-94`), consumed by
`GatewayEnforcer::apply_if_changed` (`gateway/src/enforce.rs:34`). **Before PR #43 that
propagated out of the sync loop and killed the process — loud. It is now non-fatal:** logged,
counted, retried. So a gateway first-booting against a too-new controller with no prior good
policy **attaches its default-deny enforcer and drops all fabric traffic while reporting
healthy to systemd and Kubernetes.** (Mechanism recorded at
`docs/research/proto-block-design-verification.md:174-183`.) The crash used to be the only
signal that version skew had happened; making it non-fatal removed the signal without adding
the negotiation that was supposed to replace it.

The codebase already does **ad-hoc, per-field, sentinel-based compat six times over** —
`StateSnapshot.deprecated_relays` kept as `repeated string` because changing a live field's
wire type is a hazard, `ReportRequest.peer_paths_snapshot` as an "old client" bool sentinel,
`session_generation`'s `0` legacy sentinel — with no global contract tying them together.

**The cost is still low, and v1.0 is the last free moment.** The design exists and was
verified against `main` (`backlog-program-notes.md:48`, B9 "Candidate A adopted") with exact
field numbers — `WatchRequest{2=client_version, 3=max_ir_schema}`,
`StateSnapshot{9=controller_version, 10=min_supported_version}`, `GatewayInfo{6,7}`,
`EnrollRequest{6}` — **all verified free at HEAD**. Legacy peers land on proto3 defaults
(empty version → assumed 0.3.x, `max_ir_schema = 0` → treated as 1) and age out
automatically: no wire break, no migration. The one DB step is a `SCHEMA_V4` adding
`gateway.version` / `max_ir_schema`, with `SCHEMA_V2` (`db.rs:285-293`) as the exact
precedent. X-6's own promise is *"controller vN supports vN and vN-1"* — that contract starts
at 1.0, so the v0.x tags do not complicate it. **Ship 1.0 without the fields and v1.0 itself
becomes the permanent un-negotiable legacy peer every later version special-cases forever.**
Two known design gaps to close with it: the operator turns an enroll-time version rejection
into a **silent 15s requeue loop** (`operator/src/controllers/gateway.rs:641`) with no CR
condition naming the cause, and `--min-supported-version` is specified as "emergency
lower-only" with no ratchet anywhere in the controller. **Dependency:** the CI skew matrix
X-6 also demands depends on B4.

### B11. Client peer: three PRD requirements are written as if it exists; there is no code
**Size: ~1 week to build Phase 1, or 2 hours to de-scope. Decision, not work.**
Verified: `grep -rniE "client_peer|ClientPeer|is_client"` across `crates/` returns **zero
hits**; there is no client crate, no client-kind token, no provisioning path. Yet
`README.md:5,19` and `PRD.md:21` advertise the component, and **G-4a, X-8 and the amended
Non-Goals item 1 are all written as live requirements** — X-8 in particular pre-declares six
guarantees a phase-1 client would not satisfy and requires that *"every limitation above is
documented wherever clients are provisioned"*, which is nowhere. Phase 1 is scoped as "small,
days" in `docs/research/client-component-scoping.md:136` and its owner decisions are settled
(operator-chosen range, mandatory fail-closed conflict preflight, ~a dozen `client × segment`
pairs against `MAX_RULES`). Either build it or mark G-4a/X-8 post-v1 in the PRD — shipping
1.0 with them as written is a documented-but-unbuilt claim of exactly the class this project
has a history of. **Related and worth stating in the same release note:** the macOS and
Windows release jobs ship the **admin CLI only** (`release.yml:126,187` — macOS gets
`fabricctl`/controller/relay/mkcerts, Windows gets `fabricctl` alone). **There is no
data-plane artifact for either OS**, and Non-Goals item 5 (Linux-only gateways) is unchanged
and still stands.

## Group 2 — Should-fix (shippable if documented)

### S1. Relay `case5` — a departing peer never unpins the survivor (RED `#[ignore]`, still committed)
**Size: 1–2 weeks; depends on the item-19 relay-mux decisions.**
`crates/wiremesh-gateway/tests/relay_matrix.rs:2026`,
`case5_peer_departure_unpins_survivor_from_relayed`, is the **one remaining `#[ignore]` in the
entire workspace** and is RED-by-design: *"Un-ignore when NO_ROUTE / per-peer route presence
lands (item 3b)."* The mechanism: `run_path_ticks`'s `healthy_relay` map means "the shared QUIC
connection is alive", not "this peer is reachable through this relay". Its doc comment also
records a second latent hazard — `to_relay_died` reading `death_reason() == None` lands in the
right branch *"right by accident"*. Worth saying out loud: the "last RED-by-design ignore
cleared in v0.9.1" framing is true of rotation only; this one survives.

### S2. Rotation still resets every peer's session (`replace_peers`)
**Size: 3–5 days.**
`uapi::encode_set` (`uapi.rs:171`) unconditionally emits `replace_peers=true`, which in
boringtun 0.6 is `clear_peers()`. The **endpoint/punch/relay path was fixed** —
`main.rs:apply_peer_endpoint_scoped` → `uapi::set_one_peer` (`uapi.rs:244`), pinned by
`tests/scoped_peer_apply.rs`. The **rotation path was not**: `apply_state` (`main.rs:3487`)
routes any peer *modification* (which a rotation promote is) and any header change
(`private_key`/`listen_port`, i.e. every Role-A cutover) into the full apply.
`rotation.rs:436-441` documents this as intended. Consequence: one gateway's rotation resets
N−1 innocent peers' Noise sessions. **No test can currently observe it** — both netns rotation
topologies have exactly one peer, which is also why it survived. The primitive to fix it
already exists and is proven; extending it is the work. Ties to backlog item 4 (three-gateway
harness), which is the prerequisite for ever testing this.

### S3. `Retire{0}` permanent wedge (backlog item 5) — CONFIRMED OPEN, all three sites
**Size: 2–3 days.**
`prior_active_epoch` is still `u32` (not `Option<u32>`) at `sync.rs:RotationTracker:275` and
`controller/src/rotation.rs:RotationState:42`, with `.unwrap_or(0)` intact at all three sites
the backlog names: `drive_rotation_for` (`sync.rs:833-837`), `sweep_rotations` step 2
(`sync.rs:1176-1180`), and `report`'s batched seed loop (`sync.rs:1893-1898`).
`rotation.rs:decide` rule 1 (L57-63) emits `Retire { epoch: 0 }` with no guard, and
`evict_decision` (`sync.rs:325`) returns keep on `None`. Permanent by construction. Another
gate on re-enabling the timer.

### S4. Controller and relay export no metrics at all (PRD X-2, P0)
**Size: 1–2 weeks.**
No `prometheus` dependency exists in any crate; the gateway hand-rolls
`crates/wiremesh-gateway/src/metrics.rs` (342 lines) and is the **only** component with
metrics. No `wiremesh_controller_*` or `wiremesh_relay_*` symbol exists anywhere. For a system
whose defining property is fail-static, you cannot scrape whether the control plane is
healthy. Also missing: any metrics *documentation*, the reference Grafana dashboard X-2 and
spec §8 both promise (no `*grafana*` or dashboard JSON in the repo), and the

### S5. Operator reconcile loops have zero automated coverage
**Size: 1–2 weeks for a `kind` harness.**
Confirmed by grep: no `kube::Api`, `kube::Client`, `httpmock`, `wiremock` or `tower_test`

### S6. `spike/` should leave the repository
**Size: 1 hour. Highest value-to-risk ratio on the list.**
Eight directories of self-described throwaway Phase-0 code, each with its own `Cargo.lock`.
Correctly excluded from the workspace (`Cargo.toml:8`) and from images (`.dockerignore:9`),
and no production crate depends on it. But its five lockfiles generate **8 of the 10 open
Dependabot alerts**, which is how a real alert gets missed, and `README.md:113` tells readers
to run its tests. Delete it or move it to an archive branch; git history and
`docs/research/phase0-report.md` preserve the record.

### S7. Dependabot: 2 real advisories, both transitive via boringtun, neither fixable by bump
**Size: assess + document, 1 day.**
Root `Cargo.lock` carries **`ring 0.16.20`** (GHSA-4p46-pwfr-66x6 / CVE-2025-4432, AES/QUIC
header-protection panic) pulled in *solely* by `boringtun 0.6.0` — which is the latest
crates.io release, so bumping cannot fix it. **The panic requires `overflow-checks = true`; I
verified the workspace sets no `[profile.release]` overrides and the Dockerfile passes no
RUSTFLAGS, so release binaries have overflow checks off and the advisory is not live in
shipped artifacts** — but that reasoning must be written down, because the affected QUIC
header-protection path is exactly what `wiremesh-relay` exercises and an attacker-inducible
panic in a relay is a DoS. Also present: **`curve25519-dalek 4.0.0-rc.3`** — a release
candidate, below the 4.1.3 fix. Shipping a crypto RC in a 1.0 is a poor look independent of
the timing advisory. Note the workspace deliberately disables `prefer-post-quantum` on rustls
(well-reasoned, `Cargo.toml`), so there is no PQ hybrid key exchange in v1.0 — worth a release
note.

### S8. `wiremesh-gateway`'s mutex discipline is a correlated-failure design
**Size: days to weeks depending on ambition; at minimum, document.**
101 `.unwrap()`/`.expect()` in the production region of `main.rs`, 88 of them
`std::sync::Mutex::lock().unwrap()` on shared state (`ctx.paths`, `ctx.active`, `ctx.desired`,
`ctx.punch_backoff`, `ctx.relay_pointed`, …). One panic inside any critical section poisons the
mutex and every subsequent lock in every other task panics too — a single bug degrades to
total gateway unavailability. `wiremesh-relay` (15 total) shows the team knows how to avoid
this; the gateway was not held to the same bar. Related: 8 `unreachable!()` in
`wiremesh-policy/src/compile.rs`, load-bearing on `compile()` receiving pre-validated input,
where `validate.rs:199` already documents one prior escape.

### S9. Config options the nftables backend silently ignores
**Size: 1 day.** `crates/wiremesh-enforcer/src/nft.rs:198` (and siblings in `ebpf.rs`) carry
`#[allow(dead_code)]` flow-table / idle-timeout / rate-cap config fields that the nft backend
accepts and never applies. A knob that silently does nothing is a v1.0 behaviour bug — either
wire it, reject it, or document the divergence next to the existing ratified one.

### S10. Backup, restore, DR, and PKI lifecycle are undocumented
**Size: 1 week.** Backup is one sentence (`install.md:70`). **There is no restore procedure at
all** — the nearest thing is step 4.3 of a private zolab→FI migration runbook. No DR document,
no RTO/RPO, no gateway-loss recovery. **Certificate lifecycle is essentially absent:** the CA
is 10-year, but nothing documents leaf/gateway cert lifetime, renewal, or what an operator sees
when a gateway cert expires, and there is no CA-rotation story. PRD **C-10** requires the
CA-rotation and compromise runbooks to *"be executed as integration tests, not just
documented"* — currently neither.

### S11. No upgrade path, and the schema versioning is invisible
**Size: 3–5 days.** The only upgrade content is one narrow case (`install.md:112-161`, the
`/var/lib/wiremesh` relocation) plus the Helm CRD re-apply note. No stopping order, no
component skew guidance, no rollback. The code *does* version its state — controller SQLite
`PRAGMA user_version` is at **3** with forward-only migrations at
`wiremesh-controller/src/db.rs:285,297` — and **none of it is mentioned in any operator-facing
doc**, so nobody is warned that rolling a binary back from `user_version=3` to a `=2` build is
undefined. Gateway `state.json` has careful `#[serde(default)]` compatibility shims and **no
format-version field at all**. Policy IR has schema 1 and 2 both live in tests. CRDs are all
`v1alpha1` with no conversion webhook, so `v1beta1` will be a breaking manual migration.

### S12. Host prerequisites documented only for the `.deb`/`.rpm` path
**Size: 1 day.** `install.md:55` correctly notes the packages pull `iproute2 nftables conntrack
procps`, and the relay's 0600 requirement is documented well (`install.md:296-300`). But
tarball and container users are told nothing, **no minimum kernel version or eBPF/tc(clsact)
requirement is stated anywhere**, and the fact that the gateway mutates host
`net.ipv4.ip_forward` and rp_filter via `sysctl` appears only in `CLAUDE.md`, which ships to
nobody who reads it as documentation.

### S13. Landmines known internally, absent from user docs
**Size: 2 days.** Promote from `BACKLOG.md` into `install.md`/`operator.md`: **no gateway HA**
(item 21 — and specifically that a node autoscaler makes it *worse* than a single box, since
the identity is on a node-local RWO PVC); **routes carry no `src`** (item 12 — see U1 below,
the mechanism is sharper than the item states); **IPv4-only** (mentioned once, in passing,
inside an unrelated `operator.md` table); **LAN-side route propagation** (item 20 — documented
honestly at `operator.md:311-318` but only in the Kubernetes doc, not in `install.md`).

## Unwritten findings — things I could not find recorded anywhere

**U1. The gateway never assigns an address to its tun device, and every netns test papers over
it.** Backlog item 12 says "fabric routes carry no `src`". The mechanism is sharper than that:
`crates/wiremesh-gateway/src/routes.rs` does only `ip link set <if> up mtu <n>` (`:16`) and
`ip route replace <cidr> dev <if>` (`:47`). A repo-wide sweep of every `Command::new("ip")`
invocation in `wiremesh-gateway` and `wiremesh-enforcer` finds **no `ip addr add` anywhere** —
the tun is unnumbered in production, so there is no source address to carry, not merely a
missing `src` option. Meanwhile
`crates/wiremesh-testkit/src/netns.rs:377` runs `ip addr add <my_ip> dev wg0` **in the test
harness**. Every netns done-bar that proves the data plane — mesh milestone, NAT matrix, relay
matrix, rotation zero-drop, enforcement conformance — therefore runs on a **hand-numbered
topology the shipped binary does not produce**. The tests are not wrong, but they validate a
configuration the product does not create, and that gap is what item 12 experiences as a
symptom. This should be stated in item 12 and either fixed (assign an address, or add `src` to
the route) or explicitly documented as an operator step. **Size: 1–2 days to fix, plus a test
that asserts the production path produces the topology the tests assume.**

**U2. The controller `--help` DEPLOYMENT block gives three instructions that stopped working in
v0.8.0.** Detailed in the table above (`cli.rs:109-129` vs `crd.rs:63` / `workloads.rs:485`).
The outcome is benign only because backlog item 2a inverted its own prescription and chose
`off` as the operator's default — so the help text is wrong in the safe direction *by
accident*. This is the third instance of the same defect class on this project (v0.7.4 `--help`
overclaim, item 22's false `kind` e2e assurance), which suggests the class is worth a check
rather than another one-off fix: any doc comment or help text that asserts what *another*
component does should be pinned by a test or deleted.

**U3. `wiremesh-operator` is outside the release versioning entirely.** `scripts/set-version.sh`
enumerates four crates by name; the operator is not one of them, yet it is built and pushed as a
container image by `container-images.yml`. Nothing detects this — there is no test that the
stamped set matches the shipped set. **Size: 2 hours, and add an assertion.**

**U4. `key_rotation.rs` un-ignoring is unverified by machine, and cannot be.** The in-step done
bar is green *by assertion in a doc comment*; because no CI runs `--features netns-tests`
(B4), nothing anywhere confirms it stays green. Every "proven" claim in this project currently
rests on a human or an agent having run the suite locally in a privileged container. That is
the real reason B4 is a blocker rather than a should-fix.
